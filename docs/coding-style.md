# コーディング規約

採用日: 2026-09-17。自作C++は [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html) を基準に、本書の上書きと組み込み制約を適用する。本書は規約の正本であり、既存コードの一括修正やビルド設定の変更を指示するものではない。

## 適用範囲と優先順位

適用対象は新規・今後変更する自作C++コードと自作C++テストの表記である。自作の関数・クラス・構造体に対する宣言コメントも本書に従う。WCH SDK、CANopenNode、その他の外部ライブラリは上流規約を維持し、規約適合のために改変しない。

優先順位は、ユーザーが指定したプロジェクト上書き、本書に定める組み込み制約、Googleガイドの順とする。Googleガイドの変更を言語版や依存ライブラリの自動更新理由にしない。新たな衝突を見つけた場合は内容を記録し、採用方針を確認してから関連文書を更新する。

## 言語版とファイル

- 自作C++の目標言語版はC++20とする。C++23以降の機能を使わない。
- 自作C++の実装ファイルは`.cpp`、ヘッダは`.hpp`とする。Googleの`.cc`/`.h`に対するプロジェクト例外である。
- `config/`配下の役割別設定ヘッダも`.hpp`とする。ファイル名の付け方自体はGoogleに従う。
- 外部Cコードや既存の`src/main.c`を、この文書更新で改名・移植しない。

C++20へのコンパイル設定、コンパイラ・標準ライブラリの必要機能、CのSDK/スタックとのリンク、WCH割込み属性への適合はP-02で確認する。現在の点滅サンプルのビルド成功はC++20適合の証拠ではない。設定を変更した際はT-20で実際のコンパイルオプションとリンク結果を検証する。

## 書式と命名

インデント単位は4スペースとし、タブをインデントに使わない。拡張子とインデント以外の書式・命名はGoogleを基準とし、既存コードのローカル書式を新規コードの優先規則にしない。代表例は次のとおり。

| 対象 | 例 |
|---|---|
| 型（クラス・構造体等） | `PwmConfig` |
| 通常の関数 | `ApplyConfig()` |
| 変数・引数 | `output_limit` |
| クラスのデータメンバー | `output_limit_` |
| 構造体のデータメンバー | `output_limit` |
| 定数 | `kMaxOutput` |

アクセサ等のGoogle側の例外も同ガイドに従う。SDK/ABIが要求する既存シンボルやレジスタ名を命名規約のために変更しない。

## 宣言のDoxygenコメント

自作の関数、クラス、構造体は宣言の直前にDoxygen形式のコメントを必ず付ける。公開APIだけでなく、private関数、コンストラクタ、デストラクタ、アクセサ、テンプレートも対象とし、「自明なので省略」は認めない。

宣言と定義が分かれる関数では、利用契約を宣言側に置く。定義側には必要に応じて実装理由を補足する。インライン関数、クラス・構造体の本体、`.cpp`内だけで定義する関数のように定義が宣言を兼ねる場合、その直前に記載する。コメントのためだけに不要な前方宣言を追加しない。

コメントは目的、入力と出力、戻り値、前提、失敗時の扱いを必要に応じて説明する。ISRからの呼出し可否、共有状態、ブロッキングの有無、参照の寿命等が契約に関係する場合も明記する。クラス・構造体には役割と不変条件を示す。戻り値や引数がない場合に架空の説明欄を作らない。

次はコメント形式の例であり、確定したAPIや実装ではない。

```cpp
/**
 * @brief PWMの出力設定を保持する。
 */
struct PwmConfig {
    uint16_t output_limit;
};

/**
 * @brief 検証済みの設定を反映する。
 * @param[in] config 反映する設定。
 * @return 反映に成功した場合はtrue。
 * @note ISRからは呼び出さない。
 */
bool ApplyConfig(const PwmConfig& config);
```

## 組み込み向け制約と対象外

既存の例外・RTTI・ヒープ確保の禁止、静的容量管理、短いISR、非ブロッキングの協調実行を維持する。Googleガイドで許容・例示されていることだけを理由に、動的確保を伴う機能を採用しない。抽象化や標準ライブラリの採用時には割当て、実行時間、コードサイズを確認する。

ハードウェア境界に必要なWCH/GCC割込み属性、C ABIのリンケージと固定シンボル名、レジスタアクセス、周辺機能制御、ビルド条件分岐は例外として認める。ボード/HAL/SDK接続部へ局所化し、理由と実行条件をコメントで説明する。例外をアプリケーション全体の書式・命名を崩す根拠にはしない。

OS・プロセス・スレッドを前提とする規則や、Google固有のライブラリ・ツール導入の推奨は、本ベアメタルファームウェアの適用対象から外す。これらを使うためにOS/RTOSや依存ライブラリを追加しない。ホスト試験ツールの必要性は別途評価する。

対象外とするのは規約の適用範囲であり、既存コードや上流ライブラリの削除を意味しない。同期、寿命、入力検証等、組み込みにも必要な性質まで除外しない。

## 移行と検証

既存コードの不適合は後の作業で修正する。今回の規約整備ではコードの整形、改名、コメント挿入、言語移行、ビルド設定変更を行わない。移行時は機能変更と区別できる小さな変更単位にし、関連するビルド・試験で確認する。

現状はformatter/linter未設定である。規約の採用と整形ツールの導入を区別し、ツール・版・自動検査設定はO-21、ツールチェーン適合はO-17/P-02で扱う。将来clang-format等を導入する場合も、Googleベースに4スペースの上書きを適用し、命名やDoxygenの完全性は別に検査する。

関連要求はR-22/R-28、検証は [test-plan.md](test-plan.md) のT-20/T-24、設計判断は [decisions.md](decisions.md) のD-02/D-36を参照する。
