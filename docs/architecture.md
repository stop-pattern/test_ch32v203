# アーキテクチャ設計

記録日: 2026-09-17。状態: 合意済み方針と設計案の記録／未実装。

要求の正本は [requirements.md](requirements.md)、外部契約は [interface-spec.md](interface-spec.md)、判断の根拠と未決台帳は [decisions.md](decisions.md) とする。以下のモジュール名は責務を示す設計上の名称で、作成済みのファイルや確定済みAPI名ではない。

## システム構成と責務境界

```text
PC / BIDS_Server ← USB CDC → BIDSクライアント ─┐
                                             ├→ 経路選択 → 変換 → 出力調停 → DO/PWM
CANopenマスター ← CAN → CANopen slave ────────┘                      ↑
                                                               安全状態管理
DI/ADC → 取得・フィルタ → 論理値 → 選択経路への操作通知
                              └→ 両接続経路から参照可能な状態・診断

ボードプロファイル → クロック / ピン / 周辺機能 / 電気的既定値
設定管理 → 検証済み設定 → 経路選択 / 変換 / 入出力 / 通信
診断管理 → LED / EMCY・OD / プロトコルで許された通知 / デバッグログ
```

CANopenマスターは別のESP32系プロジェクトを予定する。本リポジトリにはマスター機能を実装しない。ゲートウェイとは論理値・操作・診断を仲介する意味であり、USBフレームとCANフレームを無条件に相互転送する装置ではない。

## モジュール責務

| モジュール | 責務 | 境界 |
|---|---|---|
| Board/HAL | クロック、ピン、タイマ、ADC、CAN、USB、tick、ウォッチドッグ | レジスタ・SDK依存をここへ限定する |
| I/O acquisition | DIデバウンス、ADC取得・移動平均、校正・診断 | 通信形式を解釈しない |
| USB transport/framing | CDC、改行、B64E識別、受信上限の管理 | BIDSの意味処理と分離する |
| BIDS client | コマンド生成、応答照合、版差、push/poll、生存監視 | 解析済み値・操作をアプリケーションへ渡す |
| CAN adapter | CANドライバとCANopenNodeの接続、割込み・時刻供給 | CAN FDは実装しない |
| CANopen service | NMT/LSS/SDO/PDO/Heartbeat/EMCY、OD公開 | アプリケーションへ検証済み操作を渡す |
| Route arbitration | GPIOとビルド方針から操作権を選択する | 接続性、生存性、値の鮮度を別状態で扱う |
| Mapping/transform | 入力源と出力先の対応、線形変換、クランプ等 | 任意式評価やスクリプトを提供しない |
| Configuration | ビルド既定値、shadow設定、検証、適用 | ピンと周辺機能は実行時変更しない |
| Safety/output | 起動・故障・切替状態から最終出力を決定する | 通信処理から出力レジスタへ直接書かせない |
| Diagnostics | 状態、エラー、LED、ログ、故障原因保持 | BIDS CDCへデバッグ文字列を混入させない |
| Scheduler | 1 ms tickに基づく協調実行、固定キューの消費 | 待機ループや無制限の一括処理を避ける |

### ファイル配置との対応

配置規則は [README](../README.md) と [AGENTS](../AGENTS.md) の同一ブロックを正本とする。Board/HALは`src/hal/`、入力取得は`src/io/`、BIDSとCANopenの処理は`src/protocol/bids/`と`src/protocol/canopen/`へ置く。USB/CAN低層ドライバはhal、フレーミングやスタック接続はprotocolに分ける。経路選択・変換・実行時設定・安全出力の調停は`src/control/`、診断は`src/diagnostics/`、初期化の組立てとSchedulerは`src/app/`が担当する。

共有宣言は`include/<module>/`、内部ヘッダは対応するsrc配下、独立再利用ライブラリは`lib/<library_name>/`へ置く。これらの機能別フォルダは計画上の配置先であり、現在の`src/main.c`を移動したり、空の実装を作ったりする指示ではない。具体的なAPI・ファイル分割は未決事項の解消後に設計する。

## 実行モデルとデータフロー

C++20のベアメタル構成とする。ISRは取得・キュー投入等の短い処理に限定し、解析、設定検証、変換、状態遷移は協調ループで行う。キュー長、優先順位、1巡あたりの処理量、オーバーフロー方針はO-11で確定する。C++20のコンパイラ・標準ライブラリ・SDK境界の適合確認はP-02で行う。

受信は「フレーム成立→構文・範囲検証→経路権限確認→変換→安全状態の適用→レジスタ更新」とする。部分フレームや不正値を出力へ反映しない。有効フレーム受信からレジスタ更新までの5 ms要求を、この経路全体で検証する。

入力は「1 ms取得→デバウンスまたは平滑化→校正・変換→状態更新→選択経路への操作通知」とする。DIのキー押下/解放とADCのブレーキ段への変換を含む。モードGPIOは20 ms連続安定で確定する。切替時は旧経路へ可能な範囲で解放を通知し、新経路ではDIの解放・再押下までHorn押下を抑止する。旧経路が断線した場合の解放到達は保証しない。

通信経路ごとに、物理接続状態、通信生存時刻、個別値の更新時刻を分離する。BIDS自動送信は値が不変なら止まる可能性があるため、無更新だけで断線やpush無効を判定しない（O-05）。

## 設定とボード分離

ビルド時の既定値はリポジトリ直下の`config/`配下の役割別`.hpp`へ集約する方針とする。ボード、通信、タイミング、I/O設定を分離し、巨大な単一ヘッダを作らない。具体的なファイル名・生成方式は未確定である。ヘッダ検索パスはP-02で明示設定・検証し、自動認識を前提にしない。実行時の設定状態・検証・反映は`src/control/`に置く。

自作C++の実装は`.cpp`、ヘッダは`.hpp`とし、その他の表記と宣言コメントは [coding-style.md](coding-style.md) に従う。外部Cライブラリの名前・書式は変更しない。

ピン、物理I/O種別、必要なタイマ割当てはビルド時に決める。一意に決まる周辺機能設定は導出し、一意でなければプロファイルで明示する。実行時には論理入力源、変換、極性、安全値、PDO関連設定を揮発変更する。

既定方式ではPre-operationalでshadow設定を書き、明示applyに対する全体検証後に有効設定を一括置換する。Operational遷移だけでは未反映設定を採用しない。不正設定では有効設定を保持し、規定のSDO Abort/診断を返す。一括方式を無効化したビルドでは独立したスカラー値のみ即時適用可能にする。対象一覧と反映APIはO-04。マッピング表の途中状態は公開しない。

PWM上限Pmaxは通常の構成設定から独立した運転調整値とし、選択経路からだけ変更できる。正常出力中は現在の有効入力で次の出力更新時に再計算し、安全状態や指令失効を解除しない。USBは速度の絶対値/Vmaxを0～1へクランプしてPmax倍し、CANはPWM指令/65535をPmax倍する。USB側の変更手段、OD/API、原子的反映境界はO-04/07/08、演算精度・丸めはO-11/18。

## 安全状態と診断

起動時は安全出力とする。USB使用可能にはBIDS正常通信とDO/PWM値の取得を要求する。経路切替では最大3秒の旧値保持中に新経路のDO/PWMが両方揃ってから一括で引き継ぎ、時間切れなら両出力を安全値にする。選択経路の通常通信断は3秒後、選択CANのNMT Operational離脱とbus-offは即時安全出力へ移る。正常USB操作中の非選択CANの停止・故障では出力を停止しない。MCU共通故障は別扱いであり、切替と故障の優先順位はO-06で確定する。

回復可能な通信異常では再試行を続け、必要な運転条件と新しい有効指令が揃えば自動再開する。DO/PWMとも通信断前の指令を再利用しない。片側だけ新着した際の再開単位はO-06で確定する。致命的な初期化・内部整合異常は安全出力、RUN消灯、ERRORコード点滅で停止し、表示維持のためウォッチドッグを給餌する。通常運転の給餌条件と致命停止への遷移条件を区別する。再試行間隔、診断解除・保持、コード一覧、LED優先順位はO-10/14に残す。

## メモリと依存ライブラリ

固定配列・固定容量キューを使用し、例外、RTTI、ヒープ確保を使わない。CANopenNodeは静的確保構成（`CO_USE_GLOBALS`等）を選ぶ。WCH SDKとCANopenNodeはCのまま使用し、上流ソースを改変せずC++境界を設ける。

Flash目標56 KB、静的RAM目標14 KB。可変BIDS構造の対応でFlash目標を超える場合は、まず可変構造登録・値対応を外し、Spec/State/Handle/Panel/Soundを維持する方針とする。機能削減時は文書と試験範囲を更新する。残る不足を別機能の無断削除で解消しない。

Panel/Soundのペイロードには共有512 byte領域を使用する方針が合意済みである。ストリームBase64復号は設計候補とする。フレームヘッダ、可変構造メタデータ、スタックを含めた総量は未検証で、受信全体のバッファ構成はO-08/11/12で確定する。

## 未決事項

モジュール間の具体的な型・所有権・API、割込みとメイン処理の同期はO-11、設定適用APIはO-04、経路と故障の状態遷移表はO-06、ライブラリの固定版とビルド統合はO-17に対応する。未決部分を実装者の裁量に委ねて実装開始しない。
