# 長期・自律開発の運用規約

本書はgoalに向けて継続的に開発を進める方法を定める。現在の目的・許可範囲・実施状況は [progress.md](progress.md)、試行の根拠は [work-log.md](work-log.md) に保存する。ファームウェアの仕様は [requirements.md](requirements.md) 以下を正とし、運用手順の追加だけで機能実装を開始しない。

## 1. 目標と自律性

開始時に目的、対象/対象外、観測可能な完了条件、関連R/T/O-ID、作業段階、使用可能な実機・ログ経路、許可された変更・書き込み範囲をprogressへ記録する。既に与えられた情報と許可を引き継ぎ、同じ許可を各サイクルで求め直さない。

ユーザーがgoalの設定・開始を明示的に依頼し、Goalツールが利用可能なら現在のgoalを照会する。既存goalを重複作成せず、目的と完了条件をファイルへ対応付ける。通常の作業依頼や将来の運用説明だけからツール上のgoalを新設しない。トークン予算は明示された場合だけ設定する。

Goalツールとファイルは別の役割を持つ。ツールはgoalの稼働状態、progressは再開に必要な具体的状態を保持する。完了・blockedへの変更は使用中ツールの条件に従う。試行回数だけでblockedへ変更したり、停止時刻や残予算を理由に未完のgoalを完了扱いにしたりしない。

許可された範囲では、計画、実装、試験、ビルド、解析、修正、書き込み、デバッグを自律的に反復する。仕様判断が必要な未決事項、対象不明の実機、新たな権限が必要な操作は依存作業を止めて具体的に確認する。その間に可能な独立した調査・試験・文書作業を進める。goalの継続指示を機能範囲の拡大や保護解除等の許可と解釈しない。

| [requirements.md](requirements.md) | What/Why、要求ID、対象範囲 | 現在の要求へ統合して書き直す |

| [coding-style.md](coding-style.md) | Google基準、プロジェクト上書き、組み込み制約、移行方針 | 適用範囲・例外・検査方針を関連文書と同期 |

| [progress.md](progress.md) | 現在goal、権限、完了条件、進捗、次の行動、担当、稼働資源 | 最新状態へ置換し、短く維持 |
| [work-log.md](work-log.md) | 試行ID、操作・失敗・根拠・検証結果・引継ぎ | 日付/試行ごとに事実を記録 |
| [tooling-environment.md](tooling-environment.md) | 確認時点のCLI/依存版、導入スキル、環境検証 | 確認日と検証範囲を明示 |

開始・中断復帰・コンテキスト圧縮後は次の順で復元する。

1. AGENTSとprogressを読み、goalの範囲、最後の確認、直近の次の行動を把握する。
2. GitのHEAD・差分・未追跡ファイル、実行中エージェントとプロセスを確認する。必要ならGoalツールと実機の状態を照会する。
3. work-logの直近の関連試行と、作業対象の仕様・未決項目だけを読む。全履歴を毎回コンテキストへ取り込まない。
4. 記録と実態が違えば、未検証として差分と根拠を保存し、必要最小限の再確認を行う。消えたプロセスを成功扱いせず、既に進行中のupload等を重複起動しない。
5. progressの次の行動から継続する。ログ、成果物、担当の状態が変わった時点で再びファイルへ保存する。

## 3. 開発サイクル

| 段階 | 実施内容 | 保存するもの・次への条件 |
|---|---|---|
| 計画 | 完了条件から小さな検証可能単位へ分解し、依存と担当を決める | 試行ID、関連R/T/O、変更範囲、期待値、次の一手 |
| 実装・試験 | 仕様と試験を同期し、所有範囲内で実装する | 変更ファイル、仕様判断、テスト結果 |
| ビルド | 対象環境のCLIと依存版を確認し、安定したソース状態からビルドする | コマンド、環境、終了コード、最初の重要エラー、サイズ、成果物 |
| エラー解析 | エラーを構文/リンク/容量/実行/通信/環境等に分類し、観測と仮説を区別する | 再現条件、原因仮説の要旨、根拠、次に切り分ける条件 |
| 修正・再ビルド | 一つの原因に対応する変更を行い、失敗試験と影響範囲を再確認する | 前後差、解消/未解消、回帰結果 |
| 書き込み | 許可済み対象、ビルド識別、実機・プローブの専有を確認して実行する | 実際の書込み成果物のハッシュ、環境、対象、検証・リセット結果 |
| デバッグ | 必要なログ・波形を有限の観測条件で取得し期待値と比較する | ログ経路、期間、再現操作、観測値、欠落、分析結果 |
| 統合・継続 | 文書を再構成し、サブエージェント成果を確認、検証して小さくコミットする | 結果、残件、次の行動、コミットとの対応 |

デバッグで異常を観測したら解析へ戻る。ビルド成功だけでサイクルを完了せず、当該作業の完了条件まで継続する。文書のみの変更など、書込み/HILを必要としない作業は該当段階を対象外と記録する。

同じ失敗に対しては、仮説、計測方法、入力、コード、外部状態のどれが変わったかを残して再試行する。観測条件を変えて原因を調べる再試行も認める。無変更・無期限のリトライで進捗を装わず、原因が絞れなければread-only解析を別エージェントへ委譲する。再試行上限や待ち時間が必要な処理は、開始前に根拠と終了条件を記録する。

## 4. 保存する粒度と証拠

新しい事実、ユーザーの回答、設計判断、変更、コマンド結果、失敗、仮説の棄却、委任結果、検証完了を得た時点で必要情報をファイルへ書く。長いコマンドや委任の前には予定と所有者、開始後はPID/セッションID等、終了後は結果を保存する。会話の終了、休止、引継ぎの前にもチェックポイントを更新する。再開に必要な小さな進捗を最終報告まで溜めない。

各試行には少なくとも次を残す。

- 日時とタイムゾーン、作業/試行ID、目的、関連要求と試験、担当。
- 実行ディレクトリ、コマンド、環境・設定、ソースコミット、未コミット差分の有無と識別、終了コード。
- 観測事実、重要なエラー/ログ抜粋、原因仮説の要旨、適用した修正、比較結果。
- ビルド/書込みの場合は成果物パスとSHA-256、実際のボード・プローブ・ポートの識別、操作前後の状態。
- 合格/不合格/未実施/対象外、残る不確実性、次の具体的な操作、継続中プロセスと終了方法。

詳細なビルド/シリアル/デバッグログは例として`.pio/logs/<試行ID>/`に保存し、要点とパスをwork-logへ記録する。標準出力と標準エラー、元コマンドの終了コードを失わない。生ログには期間・サイズ上限を設け、継続する場合はローテーションする。重要な解析根拠はGit管理文書にも抜粋し、消え得る`.pio/`だけに唯一の証拠を置かない。再現に生ログが不可欠なら適切な保存先を確保して参照し、削除・移動前に参照を更新する。

work-logが大きくなったら完了した記録を`docs/work-log/`配下の日付別ファイルへ移し、索引リンクを残す。移動時に情報や根拠を捨てず、progressには現在の再開情報だけを残す。秘密情報はログに収録しない。

## 5. 並列化と所有権

親エージェントはread-onlyの仕様調査、コード調査、ログ解析、原因の独立検証、レビューを積極的に委譲する。実装、試験、文書編集も、入出力と所有ファイルが分けられる場合は並列化する。独立した作業がない場合に、同じ調査を重複させるためだけに増員しない。

委任時には目的、入力ファイル/証拠、read-onlyか編集可か、所有ファイル、変更禁止範囲、成果物、完了条件、利用可能な資源を指定する。子エージェントにも必要な仕様とスキルを参照させる。調査結果は根拠、実施した検証、未確認点、次の提案を含めて返す。

親はprogress/work-log、共有仕様の統合、Gitインデックス/コミットを所有する。子の結果を受信したら親が速やかに記録する。長時間の調査では中間結果も返し、必要なら子専用の記録ファイルを割り当てる。別エージェント所有のファイルを同時編集せず、担当変更は通知してから所有権を移す。

同じビルドディレクトリ、可変ソースツリー、パッケージ更新、実機、プローブ、シリアルポート、OpenOCD/GDBセッション、Git操作を競合させない。親が操作を直列化し、並列ビルドには独立したソース/出力領域を用意する。progressの所有者表は引継ぎ情報であり、それ自体をOSの排他ロックと見なさない。

統合時は差分、根拠、試験結果を親が確認し、別作業の変更や未確定仕様を混入させない。子の「完了」報告をそのままgoal達成と扱わず、統合後の状態を検証する。

## 6. 書き込みとログ解析の再現性

CLIや環境別手順は [PlatformIOスキル](../skills/ch32v203-platformio/SKILL.md) を利用する。書込み前から結果を記録し終えるまで、対象ソース・生成物と実機資源を確保する。`run -t upload`が再ビルドする場合もあるため、過去のビルドハッシュではなく実際に書いた最終成果物を記録する。

デバッグでは最初に仮説、観測方法、取得時間または終了イベント、期待値を定める。モニタが無出力のまま終了しない状態を放置しない。必要なら起動/リセット前からログ取得を開始し、その操作と観測開始の順序も残す。書込み検証、リセット、起動、機能動作、タイミング合格は別々に判定する。

BIDS CDCへデバッグ文字列を混在させず、確定したログバックエンドを使う。ログ経路が未実装/未確定ならその事実を記録し、推測したCOMポートで動作成功を宣言しない。書込み失敗時に自動でeraseや保護解除へ進まず、既存の許可範囲で切り分ける。

## 7. 文書の整合性維持

情報の追加・削除・変更時は、項目名、ID、数値、旧表現をリポジトリ全体から検索し、要求、構成、I/O/通信、試験、計画、判断台帳、AGENTS、スキルへの影響を確認する。正本を更新したうえで、関係する段落、表、図、例、参照を同じ変更単位で再構成する。

現行文書は「その項目が最初からそう定義されていた」一貫した文章を目標とし、末尾に訂正や例外を足して古い規則を有効なまま残さない。変更の理由や却下案はdecisionsに、実施時点の履歴はwork-log/Gitに置く。過去の測定結果は時点を明示して保持し、現状へ書き換えて証拠を失わない。

削除時は孤立した要求・試験・リンクをなくし、IDを別の意味で使い回さない。未決事項が解決したら決定と理由を確定欄へ移し、未決参照と依存を更新する。仕様未確定や未測定の事柄を整形作業で確定に変えない。スキルの原本と導入先も同期する。

チェックポイントごとに必要な文書を再読し、コミット前にはリンク、ID、要求と試験の対応、数値/状態/用語の一致を検査する。軽微な文書変更に無関係な実機試験は追加しない。

## 8. コミット・完了・引継ぎ

意味のまとまりが整合して検証できた時点で小さくコミットする。大きなgoalの終了まで保存を待たず、必要な失敗調査も事実として記録する。他者の変更や生成物を混在させず、検証未完ならその状態を記載する。Git操作は親が行う。

自分自身のコミットIDをファイル内へ埋めるための追加コミットを繰り返さない。progressには確認済みの基準コミットや作業IDを記し、当該変更のIDはGit履歴で特定できるようにする。

完了には、合意した受入条件を満たす証拠、必要な試験/HIL、文書整合、残件の明示、バックグラウンド処理・資源所有の整理が必要である。必要なHILが実施できなければ完了にせず、何が不足するか記録する。中断・外部待ちでは観測した阻害条件、試した対処、必要な入力、再開手順をprogressへ保存する。無人運転は配線変更や未決の製品判断を代行できることを意味しない。
