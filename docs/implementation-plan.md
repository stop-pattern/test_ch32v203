記録日: 2026-09-17。状態: 実装開始前。今回行うのは仕様文書の保存のみであり、以下の実装・ビルド設定変更・書込みは開始しない。

要求は [requirements.md](requirements.md)、責務は [architecture.md](architecture.md)、外部契約は [interface-spec.md](interface-spec.md)、検証は [test-plan.md](test-plan.md)、判断・未決は [decisions.md](decisions.md) を参照する。

## 開始条件

実装は、ユーザーが十分に仕様が固まったと判断し、明示的に開始を指示した後に行う。未決事項を作業者が埋めて実装開始しない。特に設定反映（O-04）、通信取得（O-05）、経路・安全状態（O-06）、OD/BIDS契約（O-07/08）、診断・復帰（O-09/10/14）、処理資源（O-11/12）を先に確定する。

基板の導通・クロック確認、参照プロトコル調査、メモリ見積り等の仕様検討と、機能コードの実装を区別する。製品VID/PIDや将来CAN FD等は試作対象外として延期できるが、今回使う値や適用範囲は明示する。

## 容量と機能範囲の確認ゲート

P-02で空の統合構成、P-05/P-06で各通信追加後、P-07で全体のFlash/RAMを確認する。実装末期までサイズ評価を延期しない。Flash目標56 KB超過時は合意済み優先順位に従い可変BIDS構造対応を先に外す候補とし、影響と試験範囲を文書に反映する。それでも不足する場合やスタック余裕がない場合は未決事項として戻し、無断で機能や安全処理を削除しない。

ライブラリは選択機能とビルド設定で縮小し、上流ソースを手作業で切り詰めない。CANopenNode、WCH SDK、参照したBIDSコードのライセンス義務を確認し、必要な通知を保存する。

## 日々の作業方法

各作業前に関連する仕様・設計・未決台帳を再読する。回答や設計変更を得たら、まず該当文書と決定理由を更新して保存し、矛盾がないことを確認する。会話の記憶だけを正本にしない。

実装開始後は小さな動作単位で「仕様更新→必要な試験→実装→対象ビルド→必要なHIL→結果記録」を回す。実機書込みは対象ボードと配線を確認して行う。仕様未確定や外部設備不在は試験待ちとして扱い、見かけ上の完了にしない。

コミットは意味のまとまりごとに行い、他の作業者の変更を混在させない。既存履歴の形式に合わせ、例えば`document firmware specifications`、`add bids parser tests`のような短い小文字の命令形とする。生成物や`.pio/`を含めない。仕様変更時は対応する要求ID、試験、判断理由を同じ変更単位で更新する。

既存`AGENTS.md`は変更しない。自作部のC++17、Doxygen、coverage方針は今回のユーザー合意を優先し、詳細スタイルはO-21で補う。関数宣言のコメントには目的、引数、戻り値と、該当する場合は副作用やISR利用条件を記載する方針とする。

## 未決・外部依存

ESP32マスターとCAN結合試験設備は別プロジェクト依存（O-16）。カスタム基板・負荷駆動段はO-03、正式製品USB識別子はO-15として試作と分離する。固定版・試験コマンド・CIはO-17、連続運転時間等の受入条件はO-13に残る。永続保存、CAN FD、独自更新、BIDSサーバ役は本実装順序へ含めない。
